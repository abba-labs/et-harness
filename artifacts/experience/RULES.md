# Agent 经验库规则（RULES v1.0）

设立：2026-09-09 用户指令。本文件是 `artifacts/experience/` 的**唯一约束正文**，约定 Agent 经验
文档的分类、命名、结构、维护与归档方式。它不替代 Rxxx 规则，不承载测试状态，不构成第二套结果系统。

## 1. 目的与边界

**目的**：为后续 Agent 与人工提供"直接可读、可检索、可维护"的操作经验——同一个坑不踩第二次，
同一条链路不必重新逆向。

**收录**：开发/测试/部署中获得的可复用操作知识——踩坑与解法、机制解释、执行 SOP、工具行为差异、
已上报缺陷的跟踪状态。

**不收录**：
- 测试结果与原始证据 → `records/`
- 人读验证报告 → `report/`
- 活动规则正文 → `report/design/rules/`（本目录约定如需升格为 Rxxx 规则，由用户按 R001 决定）
- 任务流水账、临时脚本、密码/令牌/探针序列号等敏感信息

**一致性红线**：本目录内容与 Rxxx 规则冲突时以 Rxxx 为准，并立即在对应文档"依据与变化"登记冲突；
与芯片/平台事实冲突时以芯片文档为准。

## 2. 目录结构（固定分类；新增分类必须先在本文件 §2 追加定义再建目录）

```text
experience/
├── RULES.md        # 本文件：唯一约束正文
├── README.md       # 索引：全量文档清单，任何增删改的最后一步是同步本索引
├── platform/       # 平台代码缺陷与行为（runner、报告、治理工具）
├── environment/    # 本机环境与工具链（沙箱、编码、PS5、路径、进程锁）
├── workflow/       # 可复用操作 SOP（测试执行、部署链、证据回路、知识整理）
├── governance/     # 治理与权威源实践教训
└── _archive/       # 已被修复/替代而退役的文档（保留可追溯，不再更新）
```

## 3. 文件命名

- 全小写 snake_case：`<主题slug>.md`，仅含 `[a-z0-9_]`，≤ 64 字符。
- **slug 即主题的稳定身份**：不放日期、不放序号、不放版本号——日期与版本写进正文"依据与变化"。
  （带日期的文件名必然越堆越乱、链接易断，明令禁止。）
- **一个文件只讲一个主题**。主题演进靠修改正文；新观察以带时间条目追加。
- 新主题写前必须查重：先看 README 索引、再翻对应分类目录——已有同一主题的文件一律追加条目，不新建。

## 4. 文件结构模板

固定章节按实际内容选用，但**"状态行"与"依据与变化"两节必须存在**：

```markdown
# <中文标题>

状态：active ｜ superseded（superseded 必须注明替代者或修复来源）
适用范围：<该经验在哪些芯片/环境/代码版本下成立>
最后核验：YYYY-MM-DD

## 现象/背景        # 可选
## 根因/机制        # 可选（未定位根因时写"待确认"，禁止把推测写成结论）
## 解法/操作        # 必须可照做：命令、顺序、前置条件
## 边界与不适用     # 可选（防止经验被过度外推）
## 依据与变化       # 必须有：带时间戳的增量条目
- YYYY-MM-DD HH:MM CST：<该次新增/修改/复核/修复的说明>
```

## 5. 书写质量红线

1. **事实与推测分离**：未定位根因标记"待确认"；已有结论被新证据动摇时，更新假说并保留修正轨迹。
2. **结论可回查**：关键结论给真实存在的证据相对链接；链接目标若在 `runs/`（计划删除的目录），
   必须注明"原始证据位于 runs/，本文为提炼存续版本"。
3. **不复制 Rxxx 规则正文**，用链接引用；发现冲突以规则为准并登记。
4. 单文件 ≤ 16 KiB；超限拆分主题或压缩，不设附件。
5. 中文正文、英文文件名；术语与芯片文档/公共契约保持一致。
6. **重复确认且无新知识 → 不修改正文**（防流水账）；有新观察/修正 → 追加带时间条目。
7. 平台缺陷被修复后：状态改 `superseded`、标注修复来源（commit/日期），正文保留供追溯。

## 6. 增、删、改、归档

| 操作 | 规则 |
|---|---|
| **增** | 新主题 → 新文件 + README 索引行；写前必须查重（§3） |
| **改** | 正文直接优化 + "依据与变化"追加带时间条目说明改了什么、为什么；历史判断的修正保留轨迹，不抹掉旧结论的存在 |
| **删** | 原则上不物理删除。整体过时 → 状态改 `superseded` → 移入 `_archive/` → README 索引同步；确属完全错误且无追溯价值的，经用户确认后删除并在 README 记一行 |
| **归档** | `_archive/` 内文件不再更新；缺陷复现需恢复时移回原分类并登记 |

## 7. 索引维护（README.md）

- 每个文件在 README 中有一行：`- [slug](<分类>/slug.md) — 一句话说明（状态）`，按分类分组。
- **索引与实际文件不一致视为违规**；任何增删改的最后一步是同步索引。

## 8. 提炼时机与来源迁移

- 提炼时机：任务闭环时、踩坑即时、缺陷上报后。
- `runs/` 中值得长期保留的经验（含 runs/tooling 下各任务审计记录里的教训）应迁入本目录，
  并在"依据与变化"注明来源文件；`runs/` 计划整体删除，迁移完成的判断标准 = 索引覆盖所有仍有
  复用价值的主题。
