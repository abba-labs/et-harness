## 1. 最终结构与可行性边界

### 1.1 Case 中只看见三类内容

```text
1）选择明确的实例，显式 reset；必要的独立访问者必须先停止。
2）IP 配置、刺激、启动、等待，顺序与硬件原理对应。
3）取得真实结果，以独立 Expected 断言。
```

配置与结果之间可以有必要的中途读回、判断、Ack、清除、再触发。三段式不是把所有 assert 强行移到函数最后。例如第一次错误码必须在恢复前读；第一次回调必须在第二次 Force 前确认。

允许的结构示意（只说明责任，不是可替换的完整测试）：

```python
def test_feature(can0, vector):
    can_handle = can0
    can_handle.reset()
    can_handle.timing_set(vector.timing)
    # 本卡规定的其余公开配置/触发命令仍须逐项出现。
    actual = can_handle.some_existing_read()
    assert actual == vector.expected
```

此段 `some_existing_read` 不是新 API；禁止原样复制。真正开发只能使用仓库已定义、已核对签名的接口。

### 1.2 “最好 20 行”不是削弱测试的许可

优先通过删去 Case 杂务、提取纯数据、拆开真正独立的目的达到 20 行。禁止分号压行、超长一行、把多个设备动作放进列表推导式，或用一个 run/check 函数藏起流程。

行数统一为：格式化后的函数正文物理代码行，不含签名、空行、独立注释和 docstring；多行参数逐行计数。另报函数总跨度、设备写调用数、设备读调用数、断言项数。不要混用逻辑行和物理行宣传削减比例。

仅仅保留 20 个下级调用就可能用尽预算；需要连续现场的算法不可能既原样展开，又在任何情况下都不超过 20 行。任务卡因此规定“可拆”或“保持连续”，而不是允许 Agent 自行砍步骤。超过目标时交付：剩余必要动作清单、实际行数、不能拆的状态关系、已完成的纯数据提取。状态标为 `READABILITY_EXCEPTION_REVIEW_REQUIRED`，不能自行标记“完全满足”。

**不得用增加 `driver.run_test()` 或固件执行整条测试的方法解决这个冲突。**

### 1.3 普通 Driver 与 reset 的边界

- 普通方法：校验必要的接口输入，编码一个命令，调用下一级，解码真实响应并返回。
- 允许已有的单目的有界 `wait_*`：只反复读同一个事实并等待条件，不能写配置、重置、重发刺激、决定整个 Case PASS。
- `reset()` 是唯一已确认的固定生命周期组合例外：CRG 硬件复位 → CAN 软件上下文复位 → 公共资源池复位。三次请求是顺序执行，不是可回滚的原子事务。
- 不能向 `reset()` 添加波特率、滤波、回环、默认 RAM 布局、Golden、Case ID 或测试模式。
- 不新增跨 IP 工作流引擎、上下文图、依赖注入框架或“自动恢复直到通过”。

## 4. 前置任务 G0：先修共用复位和实例，不开始大批瘦身

### 4.1 reset 的成功含义

当前 `CanDriver.reset()` 已调用三条命令。保持入口简短，但必须验证三步失败时不会执行后一步：

```text
CRG 请求失败：不发 CONTEXT_RESET，不清池。
CONTEXT_RESET 失败：不清池，不配置/触发下一步。
Resource reset 失败：抛错，不进入测试配置。
```

这些是一次函数的失败传播测试，不要求每条 Case 复制保护代码。不把“顺序调用”写成“原子事务”。

### 4.2 CONTEXT_RESET 清哪些，不能清哪些

必须清理所选 Service 的普通 IRQ、ECC、DMU 三类会话：真实回调绑定、事件数组、线路记录、watched/bound 标志及运行上下文；保留 can_id、descriptor、irq_manager、irq_priority 等长期依赖。代次按现有语义推进，不能从新响应拼一个假零基线。

不能直接 memset 整个 Service 或全局 Manager，也不能只清 `bound` 标志而留下 Manager 的实际绑定。用现有 Manager 的精确解绑能力处理 callback/context/line；测试共享物理线还有其他绑定时不能误关其他拥有者。失败的半绑定记录也要被识别，不能只依据本地 flags 认定无绑定。

**重要纠偏：** R 的 `handle_context_reset()` 调用 `stop_irq_capture/stop_ecc_capture/stop_dmu_capture`；这些旧函数可能写外设 mask/enable。因此它并不自动满足“CRG 后只清软件上下文”。开发者必须实际检查调用链。如果写入并非释放中断的必要动作，应改为复位后精确解绑和清软件记录；不要把旧 Stop 内的寄存器配置换个名字藏起来。保留必要的 NVIC 关闭/清 pending/注销属于中断生命周期，不是重复配置 CAN。

本命令的前提与复位范围写入 CAN 协议契约，先由真实 C/native 测试证明再迁移 Case。若某芯片 CRG 复位域与前提不符，记录该芯片差异，不能在公共层猜测。未证明条件满足时不得声称所有芯片通用。

### 4.3 资源池与独立访问者

Resource Pool 是公共的，不是 CAN 私有。CAN Message RAM 是另一块资源；不清消息 RAM不能伪称已清，禁止无条件清消息 RAM影响 March/ECC。

DMA Case 必须先停止该任务所拥有的通道并确认完成停止，处理路由/配置后才清池。不能假定停止 DMU capture 等于停止 DMA 控制器。先前异常退出留下未知访问者时停止会话并恢复到已知硬件状态，不依赖下一条普通 CAN Case 清池补救。

### 4.4 实例绑定必须一致

`can0` 必须真是实例 0，`can1` 必须真是实例 1。不能在连接配置为 can1 时造一个 can0 Driver，却把 can1 的 support/pins/limits/RAM 区域继续挂上去。

禁止 `driver.support = can_support` 和从 Case/support 反向塞 Driver 的循环依赖。建议固定为：Fixture 负责校验并构造所选 Driver；另一个只读参数对象携带同实例的 clock、layout、pins、vectors。Case 用 `can_handle = can0` 显式选择。只读参数对象不能包含可调用的硬件步骤或清理逻辑。

G0 验收必须包含配置选择 can0/can1 的软件测试、所有请求 instance_id 和映射一致；普通 HIL 只运行用户选定的代表实例，不扩成全部实例测试。

## 5. 前置任务 G1：记录和收尾先有接收位置，再删除 Case 杂务

### 5.1 收尾不是测试正文

通过现有 pytest Fixture/finalizer 放在运行侧，Case 不写闭包和 cleanup 列表。每个持有活动设备的 Fixture 必须在第一个可能修改设备的操作前登记收尾。

- CAN-only：关闭仍活动的 capture，解除绑定，保留本次结果；不因清理失败而静默成功。
- 外部盒子：停止该通道刺激、关闭盒子，不能只在函数正常末尾 close。
- DMA：先 stop、确认停止，再 deconfigure/释放所用请求路由；之后才允许资源释放。
- STIMER：停止并恢复该任务实际改变的状态；异常路径也执行。
- 主测试失败和收尾失败同时发生时，两条事实都保留；不能后错覆盖前错。
- 未使用 can0 的 can_support/DMA/外部 Case 也必须获得相应收尾，不能只给 can0 加 finalizer。

不要为每条卡建立不同的清理框架。按四类资源接入现有运行收尾，变化按真实依赖确定。

### 5.2 原始证据的确定接收方案

不允许先删 `record_observation` 再说以后补日志。先用 ECC 样板证明以下最小记录通路：

```text
真实 Driver 返回值 → 运行侧只记录该返回值 → 既有 record_observation/Canonical Result → 报告
```

具体实施边界：新增内容只放到已有 scheduling/results 职责范围，不反向导入 Case 到 Driver。可用一个运行侧 CAN 观察适配类，继承真实 CanDriver，仅在 `_request` 调用 super 成功后记录请求元数据与返回 words；必要解码复用既有 codec。它不能补发命令、改变返回值、配置硬件、设置 Expected、吞异常或判定 Feature。这样既有 wait 方法内部真实读数也能记录。

这不是要求实现全能代理：先只覆盖本批需要的命令，单文件、固定字段映射；不使用 `__getattr__` 万能转发、动态 monkeypatch 生产 API、元类、流程 DSL 或每 Case 一个子类。辅助 Driver/盒子的观测也在运行侧用等价的明确接收点保留，不能令 Case 再写几十行。

同名观测可能多次出现：每项保存执行 ID、请求顺序、实例、端点和原值，不用字典最后一次覆盖第一次。报告需要“首次错误”“最终计数”时按契约选定顺序，不任意取最后一个值。原 Expected 来自只读输入向量，运行侧不得从实际返回值反推 Expected。

采样时间/负向窗口原来记录的 elapsed 不一定包含在硬件响应里。此类字段需在专门的观测结果对象中携带时间范围，或暂保留最少的窗口记录；未接通前不能删。新增观察 API 只能采样，不替 Case判断正误。

### 5.3 报告备注

PASS 备注为空；FAIL 备注只选 FAIL 参数的失败信息、实际值、Expected 和证据位置。不能将通过参数混入。SKIP/RUN_ERROR/EVIDENCE_MISSING 等仍保留状态和原因，只是不伪装成芯片失败。展示规则在公共报告层修改，独立批次；不删除原始 PASS 证据。

## 6. 纯数据提取：具体允许搬什么

可以在 CAN 包相邻的一个纯数据模块中定义 frozen dataclass、常量和生成函数；名称表达用途，例如 Classic 内部回环配置、FD 外部配置、DMA 通道参数。

输入只能是明确的配置值、不可变 Mapping/已读取的能力数值；输出只能是现有 Model/tuple/bytes。禁止接受 CanDriver/TargetClient/ResourceDriver，禁止内部设备操作或断言测试通过。

每个提取函数都要与 B 的实际参数对象逐字段比较：

- timing 的 BRP/TSEG1/TSEG2/SJW；
- options 的十个字段，特别是 automatic_retry/protocol_exception；
- bus config 的全部字段，不默认把时间戳源改成 DISABLED；
- RAM 各 offset/count/payload 大小与覆盖范围；
- filter 的格式/type/action/ID/mask/buffer_index；
- DMA 源/目的地址、count、width、burst、接口、握手、更新模式。

不同 Case 看似重复但字段不同，必须分别命名或把差异显式作为参数；禁止为了“共用一个默认配置”改变值。不要把十个位置参数挤一行冒充可读。
