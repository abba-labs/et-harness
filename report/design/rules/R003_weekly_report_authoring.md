# R003 周报编写规则

## 1. 定位与边界

本文是平台周报的唯一写作规则，负责规定周报的事实来源、统计口径、固定结构、异常项说明和归档方式。

周报是给人阅读的阶段摘要，不是测试原始证据、项目当前状态、规则正文或详细技术分析。它可以引用这些来源，
但不得复制其职责，也不得重新判定测试结果。

固定输出位置和命名为：

```text
report/Weekly_report/YYYYMMDD_weekly_report.md
```

`YYYYMMDD`使用本期周报日期。`report/README.md`是唯一索引；`Weekly_report/`下不得再建立平行README。

## 2. 事实来源与统计口径

### 2.1 事实优先级

周报编写前必须按以下顺序核对所需事实：

1. 当前源码、Case Registry和正式IP契约：确认“当前已经实现什么、当前共有多少Case”。
2. 最近一次有效Canonical Result、HIL记录和Artifact：确认“实际测了什么、结果是什么”。
3. 当前有效的问题分析或验证报告：确认已证明的原因、待确认的推断和恢复条件。
4. `project-control`当前状态：确认本周任务范围、阶段和剩余工作。

历史周报只能用于理解上下文，禁止直接复制其数量或结论作为本周事实。

### 2.2 四类状态必须分开

```text
已开发
  = 文档、Firmware和PC代码已完成，不等于已通过硬件测试

PASS / FAIL / SKIP
  = 最近一次有效测试证据中的真实结果

未测试
  = 已有Case但没有有效执行证据，不得计入PASS、FAIL或SKIP
```

固定要求：

- 源码存在、编译通过或软件门禁通过，禁止写成硬件PASS。
- 旧SHA测试通过，但当前HEAD已经发生相关变化时，必须说明证据不是当前HEAD。
- 新增Case尚未HIL时，必须单列“待测试”，禁止并入SKIP。
- 只有测试框架按明确条件主动跳过的Case才能写SKIP。
- 部分回归不得冒充全量回归；表格必须标明统计覆盖范围。

### 2.3 数量与百分比

- `Case总数`来自当前正式Case Registry或当前稳定IP契约，不从旧报告抄写。
- 全量测试时必须满足`Case总数 = PASS + FAIL + SKIP`；不满足时必须标为部分测试，并单列未执行数量。
- `HIL通过率`只允许按`PASS / 本轮已归类Case总数`计算，并明确写成“通过率”，不得写成开发完成度。
- `项目进度`、`基础设施进度`和`IP开发进度`属于管理估算，必须基于稳定工作项范围；不得由HIL通过率冒充。
- 未建立可信工作项分母时，不写虚假的进度百分比，改写为“已完成/进行中/待开始”。
- 除非重复次数本身是本周交付或问题证据，周报不记录“实测多少轮”。

## 3. 固定报告结构

每份周报按以下顺序编写；没有内容的明细可以省略，但不得改变各类事实的含义：

```text
# 项目名称 周报

日期、项目整体进度、当前目标

## 一、基础功能设施
  按工作项列进度、完成内容和剩余边界

## 二、IP梳理与测试
  当前Case与最新有效测试汇总表
  各IP简要进展
  每个FAIL和SKIP的完整说明

## 三、本周结论与下一步
  已闭合事项、真实阻塞和下周动作

## 四、统计口径说明
  源码口径、证据日期/SHA、是否全量、当前HEAD差异
```

基础设施条目应使用“模块名称（进度或状态）+ 1至2条结果”的短格式，不写开发流水账。

## 4. IP汇总规则

IP汇总表至少包含：

| 字段 | 写法 |
|---|---|
| IP | 使用稳定IP名称，如UART、DMA、CRC |
| 当前Case总数 | 当前Registry或稳定契约中的数量 |
| PASS/FAIL/SKIP | 最近一次有效测试证据中的数量 |
| 未测试 | 当前Case中尚无有效证据的数量；为0时可省略 |
| HIL通过率 | 只有统计口径完整时才填写 |

表格后必须说明：

- 使用哪一天或哪个SHA的测试证据；
- 当前代码是否晚于该证据；
- 哪些已开发IP尚未HIL，因此没有进入结果统计。

## 5. FAIL与SKIP固定写法

### 5.1 FAIL

每个FAIL必须使用以下结构：

```text
#### FAIL Case `<case_id>`：<硬件Feature短标题>

测试目的：
用一句话说明本Case要证明的硬件能力。

测试Feature：
1. 列出本Case直接验证的原子硬件Feature。
2. 状态、IRQ、清除或恢复属于独立Feature时分别列出。

测试方法：
1. 写清复位、硬件实例和初始条件。
2. 写清`IP.REG.FIELD(bitN)`或`IP.REG.FIELD(bitM:N)`及配置值。
3. 写清输入数据、操作顺序、次数、时序或外部激励。
4. 写清读取的寄存器、外部观测和通过判据。

失败现象：
- 写出实际寄存器值、目标bit的实际状态和期望值。
- 写出哪些步骤已经执行成功、失败发生在哪个观测点。

结论：用一句或两句话明确区分正常Feature、失败Feature和仍未确认的原因。
```

固定要求：

1. `测试Feature`和`测试方法`是两个独立编号列表，均从1开始；不得把多个Feature压成一段长句。
2. 寄存器必须使用当前目标芯片的真实名称；涉及判定的字段必须写到具体bit，并写明配置值或期望值。
3. 测试方法必须与最终执行的Case源码、固件路径和本次证据一致；禁止根据预期逻辑反向编写未实际执行的步骤。
4. 失败现象只保留支撑结论的关键硬件数据，不粘贴完整Dump；十六进制数据使用`0x`前缀和足够位宽。
5. 如果一个Case的部分Feature正常，必须先在结论中明确正常部分，再指出真正失败的Feature。
6. 如果触发条件、精度预算或RTL定义尚未确认，结论必须写“暂时不能确定是硬件Feature故障，还是测试刺激与真实条件不匹配”。
7. 禁止把推断写成已经证明的根因。未完成根因闭环时，不使用“已确认是RTL缺陷”之类结论。
8. 禁止使用“状态异常”“结果不对”“可能有问题”等无法由寄存器值或外部观测复核的描述。

### 5.2 SKIP

每个SKIP必须使用以下结构：

```text
#### SKIP Case `<case_id>`

测试Feature：直接描述原计划验证的硬件功能。

测试方法：
1. 写清如果环境满足时将如何配置和激励。
2. 写清将观测什么以及如何判断。

测试现象：
- 写清停止在哪个阶段。
- 明确是否已经执行硬件激励。

SKIP原因：
- 写清缺失的Capability、Execution Mapping、接线、仪器、固件接口或确定性激励条件。
```

SKIP也必须写“测试现象”。如果在门禁阶段停止，应明确写“未配置硬件、未发送激励”；如果已经尝试激励，
应写实际观测到什么以及为什么仍不足以形成可靠判据。

## 6. 面向人的表达规则

1. 第一次出现DUT、Peer、Observer时，必须写出具体设备、IP实例和角色。例如：
   `ET6801 UART1（接收端）`、`ET6801 UART2（发送端）`。
2. 接线会影响结论时，必须写出连接关系；禁止只写“Peer发送数据”。
3. “失配帧”“自然中断”“外部参考”等术语第一次出现时，必须用一句话解释具体激励。
4. Feature描述必须贴近IP硬件行为，优先使用`M2M`、`IRQ RAW`、`FIFO Threshold`等项目通用术语，
   不使用“生命周期闭环”等无法直接对应硬件的抽象表达。
5. 测试方法使用编号步骤，说明配置、激励、观测和判据；不得只写“执行Case并检查结果”。
6. 不把原始JSON、完整寄存器Dump或长日志粘贴到周报。只保留理解结论所需的关键值，并引用正式证据路径。
7. 每个工作项保持简短，但FAIL和SKIP不得为了简短而删除Feature、方法、现象或原因。
8. 中文为主；标准IP名、寄存器名、Case ID和行业缩写保留原文。

## 7. 最小示例

```markdown
#### FAIL Case `fmac_p1_006`：Float转Q15钳位与Overflow状态

测试目的：

验证Float输入超出Q15范围时，硬件能正确钳位输出、置位Overflow状态，并支持软件清除。

测试Feature：

1. Float转Q15上下限钳位。
2. `FLOAT2FIXED_OVF_RPT`状态置位。
3. Overflow状态软件清除。

测试方法：

1. 每轮测试前通过CRG复位FMAC。
2. 配置`FMAC.CR.FLOAT2FIXED_IN_SEL(bit17)=1`，开启Float转Q15。
3. 通过`FMAC.PARAM`选择装载功能，经`FMAC.FIFO_DATA`输入`+2.0`和`-2.0`。
4. 检查Q15输出和`FMAC.SR.FLOAT2FIXED_OVF_RPT(bit12)`。
5. 分别执行规定的软件清除操作并回读`FMAC.SR.bit12`。

失败现象：

- 正负越界输出分别为`16383`和`-16384`，数值钳位正确。
- 触发后`FMAC.SR=0x08051000`，`FLOAT2FIXED_OVF_RPT(bit12)=1`。
- 软件清除后bit12仍为1；CRG复位后`FMAC.SR=0x00000001`，bit12才清零。

结论：Float转Q15钳位和Overflow置位正常；本次软件清除路径失败。
```

## 8. 发布与历史规则

- 新周报必须在`report/README.md`增加一个链接，不创建第二份索引。
- 每一期周报必须按本期日期新建`YYYYMMDD_weekly_report.md`；禁止把本期测试结果追加到上一期周报。
- 发布前必须核对表格合计、Case ID、证据日期/SHA和FAIL/SKIP数量。
- 已进入Git历史的周报是当期记录，不得用后续结论静默重写。
- 确需纠正事实时，在原文增加“勘误”并注明新证据，或在下一期周报明确引用和纠正。
- 周报不得承载新的架构规则；发现规则缺口时，按R001单独取得授权并修改对应Owner。

## 9. 完成检查

周报交付前逐项确认：

- 文件路径和`YYYYMMDD_weekly_report.md`命名正确；
- 本期结果写入本期新文件，没有追加到旧日期周报；
- `report/README.md`已经登记链接；
- 当前Case数量与最新测试证据没有混用；
- PASS、FAIL、SKIP、未测试四类状态边界清楚；
- 汇总数字可以相加闭合，百分比名称与公式一致；
- 每个FAIL都有Case标题、测试目的、编号Feature、编号方法、失败现象和结论；
- 每个FAIL的关键寄存器均写明真实寄存器名、字段、bit和配置值；
- FAIL描述与最终Case源码和本次证据一致，没有补写未执行步骤；
- 每个SKIP都有Feature、方法、现象和原因；
- 具体实例、连接和关键术语对非开发人员可理解；
- 没有把推断写成事实，也没有把软件门禁写成硬件PASS；
- 没有复制原始JSON、长日志或无关开发过程。
