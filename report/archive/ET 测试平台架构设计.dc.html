01

背景与目标

1.1　现状:手工测试 + 每 IP 一份用例

当前 ET 系列 MCU 的 IP 验证以人工手动测试为主,尚未建立自动化体系。每个 IP 由工程师针对某颗具体芯片编写一份测试代码/固件,验证时人工烧录、人工观察串口日志或示波器,人工判断通过与否。随着芯片款数(ET3101 / 6002 / 6003 / 6801 …)和 IP 数量(已盘点 27 个)持续增长,这种模式的成本与风险呈相乘放大。

现状证据 · 取自 code/boot_rom 现有测试固件
A
编译期挑用例:靠 #define UNIT_TEST_EN / NVR_SECTOR_TEST_EN + 手工注释切换,换芯片要改宏、改工程。
B
golden 值焊死在固件:如 CRC 期望值 except=0x40EFAB9E、内存基址混在测试逻辑中。
C
只有自由文本日志:靠 DPrintf("...fail") 输出,无机器可解析的 PASS/FAIL 协议。
D
ASIC 禁调试输出:#error DEBUG_OUTPUT not allowed on ROM_ASIC —— 真芯片上常无输出通道。

1.2　核心痛点

用例随芯片相乘
N 芯片 × M 个 IP = N×M 份拷贝,人力线性甚至超线性膨胀。
无法回归、不可追溯
人工判读无结构化结果,改一版芯片无法快速回归,历史结果难对比。
扩展即重构
要做老化/高低温/筛片,现有模式只能另起炉灶,无法复用功能测试资产。

1.3　设计目标

G1 用例与固件不随芯片变 —— 同一套测试意图跑遍全系列,芯片差异被数据吸收。
G2 一套用例三处执行 —— SIL(Renode)/ FPGA / HIL(真芯片)后端可插拔,用例无感。
G3 新增边际成本 O(1) —— 加芯片=2 文件,加 feature=3 文件,不改任何已有用例。
G4 可长期迭代 —— 功能测试之外,老化/压力/高低温/筛片以插件方式接入,不动核心。
G5 轻量可靠 —— 第一版最小承重核心即可跑通,容错机制内建,维护成本可控。

1.4　设计原则

分层解耦 —— 意图 / 契约 / 执行 / 适配 / 观测各司其职,依赖单向向下。
开闭原则 —— 对扩展开放、对修改关闭:新增=建文件,不改老文件。
数据驱动差异 —— 芯片差异是数据(能力表),不是代码分支。
判定权归主机 —— 固件只执行、只回原始量;PASS/FAIL 在主机,改判据不重烧。
正交可组合 —— 测什么 / 怎么编排 / 什么条件三轴独立,自由组合不相乘。

1.5　范围与非目标

✓ 在范围内
IP 功能自动化测试;SIL/FPGA/HIL 统一;能力驱动裁剪;可靠性/温度/筛片的扩展接口;结果治理与回归。
✗ 非目标(本平台不承担)
BootROM 下载协议测试(另有体系);量产 ATE 测试程序;形式化验证 / DV 仿真签核;器件建模本身。

总体架构

2.1　三面模型:控制面 · 执行脊柱 · 观测/环境面

03

控制面 · 用例 / 契约 / 能力

控制面全部运行在主机(PC)侧,是平台"做决策"的地方:决定测什么、这颗芯片跑不跑、参数多少、走哪个变体、以及最终判定。它由三个协作组件构成 —— 用例层、IP 契约、能力模型。

3.1　测试用例层

职责
用领域语言描述"一个可被验证的行为",不含芯片型号、寄存器、通信细节。① 声明能力依赖;② 调用 Target API 激励+取观测量;③ 持有判据(golden / 容差)做断言。
参数化展开
用例函数按能力表在运行时展开:@each_instance("uart") 在有 4 路的芯片上自动生成 4 条,2 路则 2 条 —— 同一个函数,不同数量。
铁律
用例中禁止出现芯片名分支(if chip==)。差异一律经能力表(数据)或变体标签处理。此规则由 CI lint 强制(第 8 章)。
tests/test_uart.py
@requires("uart.internal_loopback")
@each_instance("uart", exclude="console")
def test_uart_loopback(target, inst):
    r = target.run("uart.internal_loopback",
                   inst=inst, data=0x55AA)
    assert r.rx == 0x55AA      # 判据在主机
    assert r.errors == 0

@requires("adc.single")
def test_adc_single(target, caps):
    raw = target.run("adc.single", ch=0)
    v = decode(raw, caps.adc.result_format) # 变体分支
    assert 0.995 <= v <= 1.005

3.2　IP 契约(Contract)—— 唯一真相源

契约是全系列共享的"功能词典":定义每个 feature id 叫什么、要哪些参数、回哪些观测量、默认容差、观测优先级。它只增不删、语义冻结——已发布的 feature 语义永不改,要改就发新版本(见 3.4 变体)。

contracts/pwm.yaml
schema: 1
pwm.deadband:
  desc:    死区插入后 A/B 互补,间隔 ≥ 设定值
  args:    { inst: int, dt_ns: int }
  returns: { a2b_ns: int, b2a_ns: int }
  observe: [self, clb, scope]   # 观测优先级
  default_tolerance: { unit: ns, abs: 20 }
pwm.adc_soc_trigger:
  desc:    PWM 事件触发 ADC SOC 采样
  args:    { inst: int, event: enum }
  returns: { latency_cyc: int }
字段规范
args/returns 强类型;observe 声明可用观测手段的优先序(auto 时从前往后选可用者);default_tolerance 带单位,避免百分比/绝对值歧义。
命名归一
契约名以行为为准,不照抄任何芯片 SDK。CAN/FDCAN → can.classic / can.fd;EQEP/QEP → qep.*。同物异名在此收敛。
契约由 validate_contracts.py 做 schema 校验并纳入 CI:字段缺失、类型错误、引用未定义 feature 均挂红。

3.3　能力模型(Capability)—— 四层来源 + 四态裁决

能力回答"这个 feature 到底跑不跑、怎么跑"。关键在于区分四层能力来源,避免把"平台没做"误报成"芯片没有"。运行时对四层求交(MVP 阶段仅芯片一层即可,其余留接口)。

capabilities/et6003.yaml
chip: ET6003
schema: 1
console: { uart_inst: 0, baud: 115200 }
ip:
  uart: { present: true, instances: 4,
          internal_loopback: true, dut_insts: [1,2,3] }
  pwm:  { present: true, instances: 8, hrpwm: true,
          capture_via: clb }
  qep:  { present: true, driver_symbol: QEP }
  adc:  { present: true, instances: 3,
          preprocess_fir: true, result_format: v2,
          tolerance: { single: {abs: 0.005} } }  # per-chip 容差覆盖
  sdfm: { present: false }         # 硅片无 → skip
  clb:  { present: true, tiles: 4 }
四层能力来源(合成 = 求交)
Chip硅片有没有这个 IP / feature
Board引脚是否引出 / 有无回环夹具
Lab是否具备所需仪器(示波器/温箱)
Backend该后端是否建模(Renode 未必有)
四态裁决(缺失 → 结果)
absent(芯片无)skip · 不算失败
board/lab 缺skip · 记录原因
target 未建模xfail · 真机仍测
not_implementedfail · 平台欠账,刺眼
为何区分 absent 与 not_implemented: 前者是芯片客观没有(合理跳过),后者是平台还没实现(欠账)。若都静默 skip,覆盖率会虚高、欠账被隐藏。not_implemented 必须报 fail,逼迫补齐。

3.4　变体 / 版本机制 —— 防用例膨胀的关键

最棘手的差异:同一 feature 功能没增减,但可观测行为变了(如 ADC 结果编码 v1→v2)。既不能加新用例(重复),也不能按芯片名分支(爆炸)。

解法:给 feature 加变体标签,能力表声明走哪个变体,用例按标签分支而非按芯片名。以后任何芯片只要声明同标签,零代码复用。分支数跟"行为变体数"(极少)走,不跟芯片数走。
变体按标签分支,不认芯片名
# 能力表声明变体(数据)
adc: { result_format: v2 }   # 3101/6002=v1

# 用例按标签分支(唯一分支点)
def decode(raw, fmt):
    if fmt == "v2": return decode_v2(raw)
    return decode_v1(raw)
# 第 5、第 8 颗芯片若也是 v2 → 改能力表一行,
# 用例零改动即复用
04

执行脊柱 · 把请求送达硅片

执行脊柱负责把控制面产生的"抽象操作"可靠地送到芯片、执行、并把观测量带回。五个环节:Target API → Transport → Backend → Agent 核心 → 适配层。它们的边界都是稳定接口,内部实现可插拔。

4.1　Target API —— 用例唯一的把手

一个 Python 抽象基类,方法签名固定。用例只依赖它,看不见通信、后端、芯片。任何后端(Renode/FPGA/HW)都实现同一套接口 → 三处执行,用例无感。
require(f)查能力,决定 skip/xfail/run
run(op, **kw)执行契约操作,返回观测量对象
reset(scope)复位外设/芯片到已知态
measure(...)经观测面取物理量(第 5 章)
host/targetlib/target.py
class Target(ABC):
    @abstractmethod
    def run(self, op: str, **kw) -> Result: ...
    @abstractmethod
    def reset(self, scope="chip"): ...
    def require(self, feat) -> Verdict:  # 查能力表
        ...
# 三个后端各自实现 run/reset:
# RenodeTarget / FpgaTarget / HardwareTarget

4.2　Transport —— 抽象往返 + 协议编解码归属

Transport 定义"一次操作请求 → 一组观测量"的抽象往返,并明确承担 test_item/args ↔ 线格式的编解码(修正 v0.2 中 backend↔agent 的协议缝)。主机端与固件端共用同一份协议定义,杜绝各写各的。载体本身可插拔:同一 op 在仿真里是函数直调,在真芯片上是串口一问一答。

串口文本行协议(MVP 载体)· proto/wire.md
# 请求  host → agent
#<seq> RUN <op> <k=v ...> *<crc8>
# 应答  agent → host(可多行,END 收尾)
#<seq> OK  <k=v ...> *<crc8>
#<seq> ERR reason=... *<crc8>
#<seq> NA  reason=absent *<crc8>

#0012 RUN uart.internal_loopback inst=1 data=0x55AA *3A
#0012 OK  rx=0x55AA errors=0 *C1
动词集
PING 握手/回报版本+caps_hash · RUN 执行操作 · GET/SET 读写命名资源 · RST 复位
状态
OK 带观测量 · ERR 执行错 · NA 该芯片无此能力(固件兜底)· LOG 诊断行
大块二进制(内存 dump / 波形)走 base64 内联或分块;控制通道与被测 UART 物理分离(见 4.4)。

4.3　Backend —— 执行环境生命周期(不含观测)

Backend 只负责执行环境的生命周期:烧录 agent、复位、建立/持有 transport、与 agent 通信。它不再挂 measure()(修正 v0.2:观测是被组合的独立能力,不是 backend 的方法)。三种后端实现同一接口。

RenodeBackend · SIL
.repl 平台描述 + Python/C# 外设模型。无硬件、分钟级冒烟,跑 CI。局限:控制类 IP(ePWM/CLB)需自建模型,先覆盖数字基础 IP。
FpgaBackend · 原型
流片前在 FPGA 原型上跑真实数字逻辑与 IO,覆盖仿真难建模的控制 IP。夜批全量回归。
HardwareBackend · HIL
真芯片 + 板卡农场(labgrid)+ 仪器。承载模拟精度、波形、温度、老化。签核级。

4.4　Agent 核心 —— 片内工头(共享,不判定)

Agent 是烧在芯片里的常驻固件,内含自注册的 handler 表(feature id → 操作函数)。它接收请求、按表调度、驱动外设干活、回传原始观测量,绝不判 PASS/FAIL。核心与 handler 跨芯片共享源码。

agent/handlers/uart.c(自注册,共享)
static agent_rc op_uart_lb(const kv_t*in,resp_t*out){
  int inst = kv_int(in,"inst");
  u16 tx   = kv_hex(in,"data");
  cdrv_uart_enable_loopback(inst);  // 契约动作
  cdrv_uart_write(inst, tx);
  u16 rx = cdrv_uart_read(inst);
  resp_set_hex(out,"rx",rx);        // 只报原始量
  resp_set_int(out,"errors",cdrv_uart_errflags(inst));
  return AGENT_OK;
}
REGISTER_HANDLER("uart.internal_loopback", op_uart_lb);
主循环
收帧 → 校验 CRC/seq → 查注册表 → 调 handler → 回帧 → 喂看门狗。幂等:同 seq 重发重放缓存应答,不重复副作用。
控制通道分离
保留一路 console UART(如 UART0)专做通道、永不被测;其余实例才是 DUT。测 UART 时被测口≠通道口。单口芯片降级为需外部回环夹具。
不依赖被禁的 debug printf —— 结构化协议在 ASIC 上照跑;caps_hash 启动校验固件与能力表一致。

05

观测面与环境面 · 硅片两端

这两个面与执行脊柱正交:观测面负责"读结果"、环境面负责"写条件"。它们不属于 backend、不属于 agent,而是独立的可插拔能力,由 Target 在执行时组合调用。这是让功能测试平滑长成可靠性/温度测试的关键接缝。

5.1　观测面(Observation)—— 量的定义不变,读它的手段可换

观测面规定"一个被观测物理量的定义与单位",并附来源标签。同一个量在不同阶段可用不同手段读取,而用例与判据完全不变。三种观测手段实现同一 Observer 接口,自注册。

self最省事
芯片自读(回收字节、错误标志、寄存器计数)。数字 IP 首选,无需任何外部设备。
clb片内仪器
用 CLB(可编程逻辑)+ XBAR 在片内捕获边沿、测脉宽/间隔。大量 PWM/QEP 时序测试免示波器。
scope外部仪器
示波器/数字表/功率计,经 SCPI 读。模拟精度、真实波形、功耗的最终依据。需 Lab 能力。

5.1.1　观测策略(observation_policy)—— 按阶段自动选择

用例 observe=auto,由策略解析(修正 v0.2 写死 scope)
# policy/observation.yaml
bringup:  prefer=[scope, clb]   cross_check=on
ci:       prefer=[self, clb]    # 无仪器也能跑
release:  require=[scope]        # 强制仪器签核

# 解析规则:取 contract.observe ∩ 可用手段,
# 按 policy 优先级选第一个;require 缺失 → skip/fail
决策链
契约声明可用手段 → 能力表/Lab 声明现场具备哪些 → policy 定阶段优先级 → 三者求交后自动选。用例不写死。
cross_check 裁决规则
两源同测时:以 require 级(scope)为基准,另一源作参考;两者偏差超容差 → 报 warning 并记录,不静默,避免 flaky 掩盖问题。

5.2　环境面(Environment)—— 与观测对称的"写"侧

观测是"读",环境是"写外部世界":温箱设温、拉偏电源调压、老化台加载。它无法用 observe 表达(观测不改变被测条件),因此独立成面。所有环境设备实现同一 EnvDriver 接口,自注册,由 Campaign(第 6 章)驱动。MVP 不实现,但接口先留好。

env/base.py + env/thermotron.py(自注册)
class EnvDriver(ABC):
    def set(self, param, value): ...
    def wait_stable(self, timeout): ...   # 等到稳
    def hold(self): ...
    def release(self): ...

@register_env("thermotron")
class Thermotron(EnvDriver):
    def set(self, temp_c): ...            # 温箱设温
    def wait_stable(self, t): ...         # 等温度到位
典型设备
温箱(高低温/温循)· 可编程电源(电压拉偏/掉电)· 老化台(长时加载)· 分选机(筛片归 bin)。
生命周期语义
set → wait_stable → hold(测试期间保持) → release。wait_stable 是关键:温度未稳不得开测。

5.3　仪器同步时序 —— HIL 最易翻车处,单列说明

当观测用外部仪器(scope)时,芯片激励与仪器采集必须严格同步,否则采空或采错。这里定义标准握手,避免各用例各写一套。

① PREPARE
主机配置仪器触发条件(边沿/电平/超时),芯片配置好待发激励但未启动。
→
② ARM
仪器进入 armed 等待触发。必须先 arm 再 start,窗口内芯片不得发信号。
→
③ START
主机令 agent 启动激励(芯片是 trigger master),仪器被触发捕获。
→
④ COLLECT
主机读波形/测量值,带 collect 超时兜底;未触发→重试或判 no-trigger。
竞态要点: arm→start 之间的时间窗必须由主机顺序保证(先确认 armed 再放行 start)。
超时: collect 设上限,单次/连续采集模式由契约声明。

编排层与报告治理

编排层(Campaign)骑在用例层之上,把"一组用例 × 条件 × 重复策略 × 归档"打包成一次测试活动 —— 这是老化/高低温/筛片的统一载体。报告治理则把"一次断言"升级为"可长期积累、可回归对比的数据资产"。

插件机制与扩展性

这是平台"可长期迭代"的技术基石。核心遵循开闭原则:对扩展开放、对修改关闭。判据只有一条 —— 加新东西时,手指不落在任何旧文件上。全部通过"约定式发现 + 自注册 + 依赖倒置"实现。

7.1　真插件 vs 假插件

✗ 假插件 · 会反噬
新增 = 回去改老文件
加 IP → 回 op_table[] 加一行
加芯片 → resolve() 里加 elif
加仪器 → 改 backend 接口
每次"回去改"都可能碰坏老功能。
✓ 真插件 · 可持续
新增 = 丢一个文件,自动发现
加 IP → 扔 handlers/spi.c,宏自注册
加芯片 → 扔 capabilities/et6100.yaml
加仪器 → 扔 env/thermotron.py
核心永远不 import 插件,只认接口。

7.2　一根主干 + 五类插口

① IP 契约插口轴 X
contracts/*.yaml · tests/*.py · handlers/*.c
② 芯片适配插口轴 X

永不改动的主干
插件注册中枢
Target API · Transport

③ 观测插口轴 Z

④ 环境插口轴 Z

⑤ 编排插口轴 Y

固件端:链接期 section 自注册

08

可靠性 · 治理 · 版本兼容

架构再优雅,没有容错就无法长期运营,没有执法机制则纪律必被赶工破坏。本章定义"跑得稳"的可靠性契约、"新增不坏老功能"的治理规则、以及多版本并存的兼容策略。

8.1　可靠性契约 —— 串口丢字节、IP 挂死是常态

用例间复位隔离
每个用例前置 RST 把外设/芯片带回已知态,避免前一个用例的残留影响后一个。
命令幂等 + 序号重试
每帧带 seq;同 seq 重发不重复副作用,agent 重放缓存应答。串口丢字节可安全重试 N 次。
每帧超时兜底
主机每帧设超时,超时→重试;仍无响应→判 agent 宕,转 SWD 抓现场(仅调试用途)。
Agent 看门狗
主循环喂狗;被测 IP 挂死 → WDG 复位 → 下条 PING 重建会话,不拖垮整轮测试。
caps_hash 启动校验
PING 时 agent 回报 caps_hash,主机与本地能力表比对;不符 fail-fast,防固件/能力表漂移。
cross_check 裁决
双观测源偏差超容差 → warning + 记录,不静默(见 5.1.1),避免 flaky 掩盖真实问题。

8.2　治理与执法 —— 规则不进 CI 等于没有

禁芯片名分支
CI lint 扫 tests/,出现 if chip== / "et6003" 直接挂红。
契约/能力过 schema
validate_contracts / validate_caps 校验字段与引用,非法挂红。
新插件跑全量回归
证明新增没碰坏任何老插件,红了进不来。
变体注册需审批
新变体标签(result_format: v3)入库需 review,防变体沦为垃圾桶。
CI 三级门禁
每次 PRlint + schema 校验 + Renode 冒烟(A 类)· 分钟级
每夜FPGA + 真芯片全量(含控制类)· 生成覆盖矩阵
流片前HIL + 仪器(C 类:精度/波形/温度)· 签核报告

8.3　版本与兼容策略 —— 多芯片多版本并存不乱

契约 schema 版本
feature 语义冻结、只增不删;需变行为则发新变体 @v2,老的保留 → 老用例永远有依赖。
协议版本
PING 交换协议版本号;主机与 agent 不兼容时明确报错,不静默误解析。
能力 schema 版本
每份 capability 带 schema 号;升级 schema 时旧表可迁移或并存,capgen 辅助升级。
兼容底线: 三个版本号(契约 schema / 协议 / 能力 schema)各自独立演进,任意两端不匹配都要显式报错而非猜测。这保证不同芯片、不同代固件、不同版本平台可安全并存于同一仓库。
09

脚本端软件设计(主机 / Python)

脚本端运行在 PC 上,是"决策 + 编排 + 判定"的大脑。本章给出其内部分层、每层的软件设计规则、以及一个从用例到串口的完整调用链实例(以 uart.internal_loopback 为例)。

9.1　脚本端分层

L1 · tests/
用例层
pytest 函数;声明依赖、发起 run、持有判据。纯业务意图。
L2 · targetlib/target
Target API
抽象基类:require / run / reset / measure。用例唯一入口,屏蔽下层。
L3 · resolver
契约 + 能力解析
加载契约、查能力表、裁决 skip/xfail/run、参数化展开、注入变体。
L4 · proto client
协议客户端
把 op+参数编码为线格式帧、加 seq/CRC、解析应答、重试/超时。
L5 · backends/
后端驱动
Renode / FPGA / Hardware:烧录、复位、持有物理链路(串口句柄)。
依赖规则(单向向下)
· 上层只依赖直接下层的接口,不跨层、不反向。
· L1 只 import L2(Target),永不 import 串口/backend。
· L2 是抽象类,L5 各后端实现它 → 用例换后端零改动。
· L3 是纯函数式解析,输入契约+能力+policy,输出"跑不跑/参数/观测手段"。
· L4 与固件端共用 proto 定义(单一真相源)。

9.2　各层软件设计规则

用例层规则
① 只用 Target API 和 caps;② 判据(golden/容差)写在此层;③ 禁芯片名分支;④ 参数化交给装饰器,不手写循环;⑤ 不做 I/O、不碰串口。
Target API 规则
① 方法签名冻结,是稳定契约;② 只做"翻译成抽象操作 + 委托下层",无业务逻辑;③ 返回强类型 Result 对象;④ 任何后端实现同一套抽象方法。
解析层规则
① 无副作用纯函数;② 契约/能力/policy 三输入求交;③ 四态裁决(absent/board/target/impl);④ 命名归一在契约,不在此;⑤ 结果可缓存。
协议客户端规则
① 编解码与固件共用同一 proto;② 幂等重试(同 seq);③ 每帧超时;④ 不理解语义(只搬运 op/kv);⑤ 大块走 base64/分块。

9.3　实例:uart.internal_loopback 的脚本端调用链

L1 tests/test_uart.py
@requires("uart.internal_loopback")
@each_instance("uart", exclude="console")
def test_uart_loopback(target, inst):
    r = target.run("uart.internal_loopback",
                   inst=inst, data=0x55AA, baud=115200)
    assert r.rx == 0x55AA        # 判据
    assert r.errors == 0
L2 targetlib/target.py
class HardwareTarget(Target):
    def run(self, op, **kw) -> Result:
        self._resolver.check(op, kw)   # L3
        frame = self._proto.encode(op, kw) # L4
        raw   = self._link.xfer(frame)      # L5
        return self._proto.decode(raw)  # →Result
L3 resolver.py(纯裁决)
def check(op, kw):
  feat = contract[op]                # 契约
  cap  = caps.ip["uart"]
  if not cap.present:      pytest.skip("absent")
  if kw["inst"] == cap.console_inst:
      pytest.skip("console reserved") # 通道口
  # 参数校验 + 变体注入
L4 proto/client.py(编解码)
def encode(op, kw):
  seq = next_seq()
  body = f"{seq} RUN {op} " + kvfmt(kw)
  return f"#{body} *{crc8(body):02X}\n"
# decode: 解析 "#seq OK rx=.. errors=.." → Result
#         校验 crc/seq;NA→skip;ERR→raise;超时→重试
一句话: 用例说"测什么"→ Target 委托 → 解析层裁决"跑不跑/参数"→ 协议客户端编码成一行帧 → 后端经串口发出。golden 与断言始终在 L1,芯片差异始终在 L3 数据里。
10

固件端软件设计(Agent / C)

固件端是烧在芯片里的测试代理(Agent)。它是主机的"手脚":收帧、调度、驱动外设、回原始量,绝不判定。本章给出其分层、每层实现规则、以及基于真实 ET6x_Driver 的完整实例。

10.1　固件端分层

F1 · proto/
协议解析层
从 console UART 收字节、组帧、校验 CRC/seq、解析 verb+op+kv;幂等重放。
F2 · core/
调度核心
按 op 查自注册 handler 表,分发;组织应答帧;喂看门狗。共享,不含 IP 逻辑。
F3 · handlers/
操作实现层
每 feature 一个 op 函数:激励+观测,只调 cdrv_*,填原始量。共享源码。
F4 · adapters/common
契约动作接口
cdrv.h:与芯片无关的动作词汇,签名恒定。handler 只认这层。
F5 · adapters/<chip>
芯片适配层

10.2　实例:uart 回环的固件端实现(真实 ET6x_Driver API)

F3 handlers/uart.c(共享,自注册)
static agent_rc op_uart_lb(const kv_t*in,resp_t*out){
  int inst = kv_int(in,"inst");
  u16 tx   = kv_hex(in,"data");
  u32 baud = kv_int(in,"baud");
  cdrv_uart_config(inst, baud);        // 契约动作
  cdrv_uart_loopback(inst, true);
  u16 rx=0; u16 err=0;
  cdrv_uart_xfer(inst,&tx,&rx,&err);    // 收发一体
  cdrv_uart_loopback(inst, false);
  resp_set_hex(out,"rx", rx);          // 只回原始量
  resp_set_int(out,"errors", err);
  return AGENT_OK;                      // 不判定
}
REGISTER_HANDLER("uart.internal_loopback", op_uart_lb);
F5 adapters/et6003/cdrv_uart.c(仅此芯片)
// 契约动作 → ET6003 真实 SDK 调用
void cdrv_uart_config(int i,u32 baud){
  UART_setConfig(UARTx(i), baud,
     UART_CONFIG_WLEN_8|UART_CONFIG_STOP_ONE);
}
void cdrv_uart_loopback(int i,bool en){
  en ? UART_enableLoopback(UARTx(i))
     : UART_disableLoopback(UARTx(i));
}
void cdrv_uart_xfer(int i,u16*tx,u16*rx,u16*err){
  UART_writeCharArray(UARTx(i),(u8*)tx,2);
  UART_readCharArray (UARTx(i),(u8*)rx,2);
  *err = UART_getRxStatus(UARTx(i))       // 错误标志
       & (UART_RXSTATUS_PARITY|UART_RXSTATUS_FRAMING);
}
换芯片时只改右边: ET6002 的 UART_setConfig/enableLoopback/writeCharArray/readCharArray/getRxStatus 经核对与 ET6003 逐函数同名同参,故 cdrv_uart.c 几乎可直接复用;若某芯片 UART 改了名或位宽,差异只在这一份文件消化,handler 与上面全部不动。

for(;;){

脚本与固件的交互

脚本端(第 9 章)与固件端(第 10 章)通过 console UART 上的请求-应答行协议交互。两端共用同一份 proto 定义,一端编码、一端解码,语义对称。本章给出交互模型、真实字节级样例、和一次完整往返的端到端时序。

11.1　交互模型

请求-应答,主机主导
主机发一帧请求,固件回一帧(或多帧 + END)应答。固件不主动发起,只被动响应。
通道分离
交互走 console UART(如 UART0),被测 IP 用其它实例 → 测 UART 时通道口≠被测口,互不干扰。
共用协议定义
帧格式、verb、状态码在 proto/ 单一定义,主机 Python 与固件 C 各按它编解码,杜绝漂移。

11.2　帧结构(两端一致)

wire 格式 · 请求 / 应答
# 请求  host → agent
#<seq> <VERB> <op> <k=v> <k=v> ... *<crc8>\n     VERB∈{PING,RUN,GET,SET,RST}
# 应答  agent → host(LOG 可多行,OK/ERR/NA 收尾)
#<seq> <STATUS> <k=v> ... *<crc8>\n              STATUS∈{OK,ERR,NA,LOG}
字段: seq 幂等序号 · crc8 抗丢字节 · kv 扁平键值(hex/int/enum/b64)

11.3　完整往返:uart.internal_loopback @ ET6003 inst=1

① 主机 L1→L4 用例 run("uart.internal_loopback", inst=1, data=0x55AA, baud=115200) → 解析层放行(inst=1≠console 0)→ 协议客户端编码
主机发出 →  #0042 RUN uart.internal_loopback inst=1 data=0x55AA baud=115200 *7B\n
② 固件 F1→F2 Agent 收帧、校验 crc8=7B、seq=0042 非重复 → op_find("uart.internal_loopback") 命中 → 调 op_uart_lb
③ 固件 F3→F6 op_uart_lb → cdrv_uart_config(1,115200) → cdrv_uart_loopback(1,true) → 写 0x55AA/读回 → 读 UART_getRxStatus → err=0
↓ 实际 SDK: UART_setConfig · UART_enableLoopback · UART_writeCharArray · UART_readCharArray · UART_getRxStatus
④ 固件回应答 core 组帧,回原始观测量(不判定),同 seq
固件返回 →  #0042 OK rx=0x55AA errors=0 *C1\n
⑤ 主机 L4→L1 协议客户端校验 crc/seq → decode 成 Result(rx=0x55AA, errors=0) → 用例断言 rx==0x55AA ✓ errors==0 ✓ → PASS

11.4　异常与容错交互

串口丢字节
主机超时未收完整帧 → 重发同 seq;固件若已执行则重放缓存应答,不重复副作用。
芯片无此能力
op_find 未命中 → 固件回 #seq NA reason=absent → 主机 skip,不算失败。
IP 挂死
handler 卡住 → 看门狗复位 → 主机超时重试 N 次仍无 → 判 agent 宕,PING 重建会话。
