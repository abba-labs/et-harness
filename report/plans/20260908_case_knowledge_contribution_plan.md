# Case知识贡献机制：最小实施方案

时间：2026-09-08 14:27 CST。
状态：样稿评审阶段，尚未替换现行规则或实现。本文是实施意图，不是第二份规则正文。
范围：platform-common / docs；ET6801 CAN仅用于历史材料提炼示例，无硬件操作。

## 1. 交付目标

长期保存的是“每个Case学到了什么”，不是“每次运行产生了什么”。
每个芯片/IP/Case维护一份可被Agent直接阅读的Markdown：问题、触发条件、关键硬件现象、判断依据、处理方案及验证边界。正常通过且无新知识时保持简短。

最低身份只保留Case、芯片/通道、适用版本及必要的板卡/bitstream身份；未知就明确未知。规范只链接，不复制全文。相同Case在不同基线上的现象必须区分，不能抹平为一个当前结论。

## 2. 贡献链路与分工

`测试产生事实 → 脚本提取相关事实 → Agent提炼并合并到Case.md → 校验后保留`

- 测试层：继续产生真实Result/Observation，不为知识记录改变断言或覆盖范围。
- 脚本：从选定运行提取Case、身份、结果、失败位置及关键观测，供当次整理使用；不把日志翻译成根因，不自动生成“已解决”。
- Agent：只读目标Case已有知识及本次相关事实；必要时查规范/源码。区分事实、推测、已验证结论，合并同一问题，不追加整段运行报告。
- 校验：检查身份、重复Case、链接及基本章节，输出待审Diff；不宣称能机器证明文字根因正确。不覆盖人工内容，重复处理相同输入不产生变化。

不新建数据库、通用工作流或第二套JSON知识库。先在现有维护入口内提供事实提取、轻量检查和索引能力，不另搭一套框架。

## 3. 什么时候值得写

| 本次发现 | Case知识处理 |
|---|---|
| 首次正常通过，无异常经验 | 记一条带适用范围的验证结论；不填空的问题模板 |
| 同一基线重复PASS或同一已知失败，无新信息 | 不改知识文件；不追加时间、计数或流水账 |
| 新问题或新触发边界 | 新建一个问题段，保留最少关键观测 |
| 同一问题有新证据、修复方案或复测结果 | 更新当前摘要，并用带时间的短条目保留重要认知转折 |
| 首次修复后PASS | 记录实际覆盖；只有原失败条件和关闭条件均满足，才标记关闭 |
| 旧判断被推翻或复发 | 保留旧判断及其当时依据，追加修正/复发，不静默擦除 |

知识文件不是运行统计库。重复测试的即时结果留在当前运行工作区，不通过更新Markdown“最后测试时间”制造无意义Diff。

## 4. 保留什么、不保留什么

默认长期贡献仅为Case Markdown；不要求每Case再配JSON、ZIP、Session或报告副本。
原始Result、日志与配置仍用于执行和当次排查，留在运行工作区；知识验收后不作为默认长期归档对象。
只有无法用文字表达且会影响后续判断的最小波形/抓包等，才单独保留必要附件，在Case内说明用途和读取时机；不默认打整包。

长期Markdown需要进入Git版本管理；拟沿用现有`artifacts/records/<CHIP>/<IP>/cases/<CASE_ID>.md`固定身份路径，调整忽略与生成器边界，使知识不再被自动渲染覆盖。目录清理必须保护这些文件及明确保留的附件。具体迁移在规则固化阶段落实，本轮不移动现存记录。

知识摘要保存足以独立理解结论的关键条件、观测和版本，不以旧Run路径存在作为理解前提。需要追查原始材料时再按来源定位，不默认注入Agent上下文。
