# ET6002、ET6003、ET3101、ET6801 SDK/IP 演进与自动化测试架构修正

时间：2026-07-22 16:32 CST

范围修正：2026-07-22 16:49 CST；旧测试方法仅作 IP 语义与覆盖差异参考，不作为新平台方案输入。

## 1. 结论

按芯片先后顺序 `ET6002 -> ET6003 -> ET3101 -> ET6801` 检查当前 `D:\lihuan\vibe_code\code\SDK\git` 下的驱动、FunctionalTest 和 FPGATest 后，可以确认此前“以 IP 为主线，而不是以芯片为主线”的方向正确，但需要补上三个关键边界：

1. 稳定资产应是 **IP feature contract 和 case ID**，不是某个 SDK 函数名或现有仓内编号。
2. 芯片差异不能只放一份 chip profile；至少要分成 **芯片能力、SDK API 绑定、板卡路由、目标环境、当前测试实现覆盖** 五类事实。
3. 同一个测试语义应由 PC 端场景、DUT 固件动作和 XC7Z045 配测动作共同组成；XC7Z045 不是每个 IP 都参加，也不应在 Python 和固件两侧各复制一套芯片驱动。

现有代码已经证明该路线可行：

- 四代代码存在大量相同或近似的 IP 驱动和测试语义。
- 四个选定源码快照的 `et_test_frame.h` SHA256 完全相同：`BCE2EACFF1E4197AF87C65BCE992C5735CD1D7DE6675CFCB6FE95E6A2569BE7D`。
- ET6003 与 ET3101 的 FPGA CAN 测试文件完全相同，SHA256 为 `11B01CE72299E551CDE8E9B84D2D70A8960DEDA4FC25CF95923A364B29F7C052`。
- ET6003 和 ET6801 的 I2C FPGA 测试都保留 29 个主要用例，核心语义高度相似，差异主要集中在 pinmux、DMA 实例和芯片资源映射。

因此，新平台应优先把这些已有资产迁移成公共 contract、公共 case core 和按 SDK API family 选择的 adapter，而不是按四颗芯片重新开发四套固件和四套 pytest。

## 3. 驱动源文件视角的 IP 变化

以下清单来自各主分析快照的 `DFP/Drivers/ET*x_Driver/Src/*.c`。它适合判断 SDK 实现和命名的变化，不等同于最终芯片规格。

| 代际变化 | 保持/新增/删除 |
|---|---|
| ET6002：28 个驱动源 | `acmp, adc, aes, ahbdma, can, cordic, cortex, crc, crg, dac, eqep, etimer, flash, fmac, gpio, i2c, interrupt, misc, mpu, sdfm, spi, srpwm, stimer, sysctrl, uart, wag, wdg, xbar` |
| ET6002 -> ET6003：31 个 | 新增 `clb, fdcan, fsi, lin`；当前验证快照未见独立 `aes` 驱动 |
| ET6003 -> ET3101：31 个 | 恢复 `aes`；当前验证驱动目录未见独立 `fdcan`，但 FPGATest 内仍带 `et3x_fdcan.c/.h`，说明 FDCAN 能力不能只靠正式驱动目录判断 |
| ET3101 -> ET6801：35 个 | 新增 `dualcore, emif, ipcm, qspi, spinlock`；`eqep` 改为 `qep`；当前快照未见 `fsi` |

这里至少出现了四类平台必须吸收的变化：

- **纯新增能力**：如 `dualcore/ipcm/spinlock/emif/qspi`。
- **语义不变、实现改名**：如 `eqep -> qep`。
- **能力并入另一驱动**：ET6801 的 CAN 头文件出现 CAN FD/BRS、64 字节数据长度等能力，不再要求独立 `fdcan` 文件名。
- **验证实现与发布 SDK 不同步**：ET6003、ET3101 的 SDK 与 verification 驱动清单并不一致。

因此 profile 中不能只有 `ip.fdcan: true/false` 这种基于文件名的判断。更稳妥的表达是：

```yaml
can:
  features:
    classic: true
    fd: true
    brs: true
  sdk_binding: can_unified_fd_v1
```

## 4. 实例数量和规模也在变化

从选定 CMSIS 设备头文件的 base-address 宏抽样，可见常用数字 IP 的实例数量变化很大：

| IP | ET6002 | ET6003 | ET3101 | ET6801 |
|---|---:|---:|---:|---:|
| UART | 2 | 4 | 4 | 8 |
| SPI | 4 | 2 | 4 | 4 |
| I2C | 2 | 3 | 3 | 3 |
| CAN 控制器 | 2 | 2 | 2 | 3 |
| SRPWM 通道 | 12 | 7 | 12 | 18 |
| ADC 实例 | 3 | 2 | 3 | 3 |
| AHBDMA 实例 | 2 | 1 | 2 | 2 |
| GPIO 端口组 | 6 | 4 | 5 | 9 |
| QEP/EQEP | 2 | 2 | 2 | 6 |

这些是源码快照证据，不是规格签核值，但足以证明 pytest 不能写死 `UART1`、`SPI0` 或“所有芯片都有两个 DMA”。测试应请求一个满足条件的逻辑资源，例如：

```text
require uart instance with dma_rx and external_route
require two i2c instances routable as master/slave
require srpwm channel with deadband and trip input
```

具体选择哪个实例，由 chip profile 与 board profile 联合解析。

## 5. SDK API 的稳定区和断裂区

### 5.1 UART 是 SDK adapter 必须存在的直接证据

ET6002 UART 使用旧接口：

```text
UART_setConfig
UART_enableLoopback
UART_writeCharBlockingFIFO
```

ET6003、ET3101、ET6801 的选定验证头文件则共同使用：

```text
UART_config
UART_transmit
UART_receive
```

后三者的这组 API 名完全一致。这说明：

- `uart.txrx.polling`、`uart.loopback.internal` 等 contract 不应该变化。
- ET6002 绑定 `uart_legacy_v1` adapter。
- ET6003/ET3101/ET6801 可绑定 `uart_config_v2` adapter。
- SDK 签名变化时不新增 pytest，也不新增公共 case ID。

### 5.2 有些 API 在相邻代际高度稳定

按头文件函数/符号名抽样：

- ET6003 -> ET3101 的 UART、SPI、I2C、CAN API 名集合相同。
- ET3101 -> ET6801 的 UART、I2C、ETIMER API 名集合保持相同。
- 这部分很适合共享同一个 adapter family，只在板级和资源 profile 中换实例、pinmux、DMA request。

### 5.3 有些 IP 的 feature 集会扩展或重组

ET3101 -> ET6801 的源码差异包括：

- ADC 增加 16～31 通道枚举和一组 pre-filter/FIR/IIR 配置接口。
- CAN 增加 FD、BRS、64 字节 DLC、FIFO/queue、timestamp/timeout 等能力符号。
- SPI 增加 DMA FIFO level/transfer start level 配置，同时不再暴露旧的 `SPI_selectChip` 风格接口。
- SRPWM 的 API 集合和通道数均明显扩大。

这类变化应新增 feature contract，例如 `adc.prefilter.fir`、`can.fd.brs`，而不是把整个 ADC/CAN 测试复制成 ET6801 专版。

## 6. 现有测试代码揭示的复用规律

### 6.1 公共断言框架已经存在

四个主分析快照的 `DFP/Test/TestFrame/et_test_frame.h` 完全相同，已经提供整数、浮点、字符串、buffer 和 bool 等断言。`et_test_frame.c` 的主要差异只是空指针检查、空行和 ET6801 为串口输出补 `\r\n`。

这部分可以作为新固件测试运行时的迁移素材，但不能直接把 `printf` 文本当成长期 PC 协议。

### 6.2 相同 case 被复制，芯片差异主要散落在初始化中

ET6003 与 ET6801 的 I2C FPGA 测试都定义了 `I2C_1 ... I2C_29`。两者 diff 主要显示：

- GPIO 编号和 pinmux 宏不同。
- ET6003 使用 `AHBDMA`，ET6801 使用 `AHBDMA0`。
- 测试入口从 `I2C_PTest` 改名为 `I2C_FPGATest`。

这说明 I2C case core 可以共享，而 pinmux、DMA mux、实例选择应下沉到 board/chip adapter。

相反，ET3101 当前验证快照只保留 `I2C_1`、`I2C_2`、`PMBUS_1`。这不是“ET3101 只支持三个 I2C 功能”的证据，而是当前 verification 覆盖不足的证据。因此必须把：

```text
silicon capability
SDK binding availability
test implementation coverage
```

分开记录。

### 6.3 当前硅前/硅后复用方式还不够稳定

现有代码有 `FPGA_VERSION` 条件，但主要用于 system/clock、UART、CRG 和少量测试差异。大量 FPGATest 与 FunctionalTest 仍是两套文件；顶层入口通过注释/取消注释选择单个测试，例如：

- ET6002 `FunctionalTest_Entry()` 当前手动选择 `UART_FTest()`。
- ET6003 `FPGATest_Entry()` 当前手动选择 `LIN_PTest()`。
- ET3101 `FPGATest_Entry()` 当前手动选择 `CORDIC_21()`。
- ET6801 `FPGATest_Entry()` 中所有 IP 调用当前都被注释。

新平台不能延续这种编译前手工选择。所有可运行 case 必须注册到只读 registry，由 PC 命令按稳定 case ID 调用。

## 7. 旧测试资产的使用边界

本报告不把旧 PC 工具、旧通信协议、旧测试框架或旧目录组织作为新平台的设计依据，也不建议对其做兼容继承。

现有测试代码在本次分析中只承担两类证据作用：

- 判断同一 IP 在不同芯片上的测试语义是否相同，例如 polling、interrupt、DMA、loopback、master/slave、deadband。
- 判断差异来自 IP feature、SDK API、芯片资源、pinmux/板卡，还是仅仅来自当前仓的覆盖深度。

后续平台应重新定义协议、case registry、结果模型和 PC 编排方式。旧测试函数名、仓内编号、入口函数和执行方式都不进入公共 contract。

## 8. 修正后的平台分层

### 8.1 唯一的功能主线：IP Contract Catalog

每个 feature 定义稳定语义，而不出现芯片名、SDK 函数名或板上引脚：

```text
uart.txrx.polling.v1
uart.loopback.internal.v1
spi.master_slave.cpol_cpha.v1
i2c.master_slave.interrupt.v1
can.classic.frame_txrx.v1
can.fd.brs.v1
srpwm.deadband.basic.v1
qep.quadrature.position.v1
```

每个 contract 至少声明：输入参数、DUT 动作、fixture 角色、判定者、预期结果、timeout、是否会复位、是否破坏存储。

### 8.2 DUT 固件

```text
transport/protocol
  -> case registry and dispatcher
  -> common IP case core
  -> SDK API-family adapter
  -> chip resource adapter
  -> board/startup adapter
```

- common case core 描述“做什么”。
- SDK adapter 描述“用这版 SDK 怎么做”。
- chip adapter 提供实例、DMA request、IRQ、时钟和特殊限制。
- board adapter 提供 pinmux 和板级路由。
- `FPGA_VERSION` 应尽量收敛到 startup/clock/board adapter；只有真正语义不支持时才在 capability 中跳过，不在 case 中散布大量宏。

这样可实现同一套 case 源码分别编译成 XC7VX980T 硅前固件和真实芯片硅后固件；不同的只是 build profile 和 adapter 选择。

### 8.3 PC/pytest

```text
pytest scenario
  -> IP contract client
  -> DUT UART client
  -> XC7Z045 JTAG fixture client (optional)
  -> capability resolver
  -> result/artifact reporter
```

Python 侧的“IP driver”应是测试语义和编排接口，不应重新实现 DUT SDK API。一个场景明确拆成：

```text
dut_actions
fixture_actions
oracle
```

例如 `srpwm.deadband.basic.v1`：DUT 配置并启动 SRPWM；XC7Z045 捕获两个数字边沿并计算周期/死区；PC 合并 DUT 状态和 fixture 测量作最终判定。

### 8.4 XC7Z045 仅按需参加

| fixture mode | 适用 IP/场景 |
|---|---|
| `none` | CRC、AES、CORDIC、FMAC、CPU/cache、SRAM/TCM、DMA M2M、部分寄存器测试 |
| `monitor` | GPIO、UART、SPI、I2C、SRPWM、timer、XBAR 的数字波形/时序 |
| `stimulus` | GPIO 输入、中断、timer capture、QEP、FSI、LIN 输入 |
| `peer` | UART/SPI/I2C/CAN/FDCAN 的另一通信节点 |
| `memory_model` | QSPI、EMIF 外部存储/总线目标 |
| `fault_injector` | ACK/NACK、CRC 错、帧错误、超时、非法时序等数字故障 |

不涉及模拟精度时，XC7Z045 可以覆盖大量数字行为；ADC/DAC/ACMP 的模拟精度和电气特性仍不应由它声明 PASS。

## 9. Profile 不应再是一张大表

建议最少拆为五份可组合信息：

1. `chip_profile`：IP、实例、feature、范围、IRQ/DMA/clock 资源。
2. `sdk_binding`：源码快照 SHA、API family、头文件/库、语义适配版本。
3. `board_profile`：pinmux、引出脚、DUT 到 XC7Z045 的连线、收发器和固定短接。
4. `target_profile`：`fpga_pre_silicon`、`real_silicon`、`renode` 分别能执行和观测什么。
5. `coverage_manifest`：contract 的固件实现、pytest 实现、fixture 实现当前是否完成。

示例：

```yaml
chip: et6801
sdk_binding: et6x_sdk_api_2026_v1
ip:
  uart:
    instances: [uart0, uart1, uart2, uart3, uart4, uart5, uart6, uart7]
    features: [polling, irq, dma, internal_loopback]
  can:
    instances: [can0, can1, can2]
    features: [classic, fd, brs]
  qep:
    aliases: [eqep]
    instances: [qep0, qep1, qep2, qep3, qep4, qep5]
```

`sdk_binding` 必须带源码 revision。ET6003/ET3101 的 release SDK 和 verification 仓已经证明，仅写 `chip: et3101` 无法唯一确定当前 API 和测试覆盖。

## 10. 固件协议最低要求

新协议不必一开始很复杂，但必须具备：

```text
HELLO / protocol version / firmware build ID / chip / target environment
CAPS.GET / CASE.LIST
CASE.RUN(case_id, instance selection, args, timeout)
CASE.ABORT
EVENT.START / EVENT.MEASURE / EVENT.LOG
RESULT(PASS|FAIL|NA|UNSUPPORTED|BLOCKED|TIMEOUT|CRASH, reason, metrics)
RESET_REASON.GET
```

控制帧至少需要 version、sequence、opcode、payload length 和 CRC。UART 只负责传输；同一协议以后也可复用到其他 DUT transport。大日志和波形不要走 DUT UART，而由 XC7Z045 在 DDR 中缓存，经 JTAG 按需上传。

## 11. 对当前方案的最终修正

此前的理解“固件端和 py case 端都维护 test_case 驱动”需要改成：

```text
一份 IP Contract Catalog
一份 pytest 场景实现
一份公共 DUT case core
若干 SDK API-family adapter
若干 chip/board/target profile
一份可选 XC7Z045 fixture implementation
```

新增芯片时，正常情况只新增/选择 profile、SDK adapter 和 board adapter；新增 IP feature 时才新增 contract 和相应实现；SDK 接口变化但语义不变时只修改或新增 SDK adapter。

## 12. 建议的落地顺序

1. 先定义协议 v0.1 与 case registry，不再通过注释选择测试。
2. 从现有代码迁移 `crc.calculate.vector.v1`、`uart.loopback.internal.v1`、`i2c.master_slave.polling.v1` 三个代表 case。
3. 同时建立 ET6002 legacy UART adapter 和 ET6003+ UART adapter，验证“SDK 变化不改 case”的核心假设。
4. 用 ET6003/ET6801 的 I2C 29-case 近似代码验证 common case core + pinmux/DMA adapter 的拆分。
5. 再加入一个真正依赖 XC7Z045 的 case，例如 `srpwm.deadband.basic.v1`，验证 DUT UART 控制与 FPGA JTAG 观测的双通道协作。
6. 最后才批量迁移 CAN/FDCAN、SPI、GPIO、timer、QEP、QSPI/EMIF 等 IP。

## 13. 尚未完成和风险

- 本次没有用 datasheet/SVD 对每个实例数量和 feature 做规格级签核；表中数量是设备头文件快照证据。
- ET6003 SDK 工作区有本地改动，未把它当成唯一基线。
- 现有 FPGATest/FunctionalTest 中仍可能包含仅适用于特定 FPGA build、板卡或早期 RTL 的隐含条件，迁移时必须逐 case 标注来源 revision。
- 目前只是架构与源码分析，没有构建四颗芯片固件，也没有执行硬件测试。
